# check-crawl-quality skill 規格書（需求層蒸餾快照）

> **快照基準**：check-crawl-quality skill @ commit bf65093（2026-07-21）。
> **定位**：clean-room 重寫實驗產出的需求層蒸餾——描述**目標、硬需求、環境事實**，
> 不描述實作機制。**Non-normative**：skill 演進不回寫本檔（避免 double-source；
> 實作的單一權威恆為 `claude/skills/check-crawl-quality/`）。
> **用途**：skill 的第一份需求層文件；重大重構或移交時的規格參照；附錄記錄「只活在實作裡」的知識缺口。

## 任務

為 Claude Code 設計並撰寫一個名為 `check-crawl-quality` 的 skill。交付物：

1. 完整的 `SKILL.md`（含 frontmatter：name、description、user-invocable、argument-hint、allowed-tools）
2. 若設計需要支援檔案（腳本、reference 文件），為每一個寫出**規格**：檔名、職責、
   介面（引數 / 輸出格式 / exit code 契約）、為何需要它。

## 目標

檢查爬蟲清理後的內容品質，在資料進 RAG 知識庫**之前**攔下問題。從兩個獨立維度評估：

1. **清潔度**——內容有沒有清理階段該除掉卻殘留的 noise。
2. **RAG 適用性**——內容對向量檢索好不好用（embedding 區分度、chunk 品質）。

產出結構化品質報告：量化評分 + 依嚴重度排序的問題清單 + 可操作的修正建議。

使用方式：使用者跑 `/check-crawl-quality <path_or_source> [context_description]`，
或以中文觸發詞（「檢查爬蟲品質」「RAG 適用性」等）觸發。

## 功能需求

### F1 格式無關的資料載入
- 輸入可能是：目錄路徑、檔案路徑/glob（JSON/TXT/MD/CSV）、SQLite DB、或自然語言描述
- 需自動偵測內容欄位（結構化格式的正文欄位名不固定）
- 檢查邏輯不得依賴特定網站結構（網站無關）

### F2 Per-source 分析（不可全域稀釋）
- 資料集常由多個來源（網站/欄目）合併而成；需識別來源分群並**逐來源**檢查
- 全域統計會稀釋單一來源的嚴重問題（某來源大比例壞、但佔總量小 → 全域看不出來）；
  設計必須同時輸出全域與 per-source 兩層結果
- 無法分群時視為單一來源，照常執行

### F3 規模適應（抽樣）
- 資料量從數十筆到數萬筆不等；大量資料不需全部讀完，需有規模分級的抽樣策略
- 抽樣必須保障每個來源的最低樣本數（否則 F2 失效）
- 報告需標明抽樣比例，結果為估計值

### F4 清潔度檢查
需偵測的 noise 類型（各項獨立執行，單項失敗不影響其他）：
- 大量文件共享的重複前綴（nav 殘留等）
- 內容重複（同一內容被收錄多次）
- 連結佔比過高的文件（導覽頁、目錄頁）
- 空白或過短的文件（需區分「空佔位」與「薄內容」——處置不同）
- web 技術殘留（HTML 標籤、JS、CSS、編碼實體、未解析的 PDF 原始資料、UI 按鈕文字）
- 結構異常（標題層級、巢狀、空行、內容截斷）

### F5 RAG 適用性檢查
- **內容-metadata 分離**：metadata（key-value 前綴、與獨立欄位重複的 title/author 等）
  混在 content 裡會傷檢索——需偵測混入比例與影響範圍
- **Chunk 品質**：開頭區分度（多筆文件開頭雷同 → embedding 難以區分）、
  大小適當性（太短缺語義、太長超出 embedding 有效上下文、異常巨大多半是解析錯誤）、
  自足性（分割後的 chunk 以代名詞/接續語開頭 → 分割點不佳；中英文接續語都要認）

### F6 評分
- 兩維度各自 0-100 評分，再合成綜合分；需定義分數區間的語意（可直接用 / 需改善 / 重做）
- Per-source 的問題須反映進總分（依佔比加權），不得被全域平均洗掉
- 各檢查項對分數的影響需有明確規則（哪項、多嚴重、扣多少），不可憑印象打分

### F7 報告
- 結構化輸出：統計總覽、評分表、問題清單（依嚴重度排序，每項附影響範圍、
  具體範例、修正方向）、per-source 摘要、依優先序的清理建議
- 每個發現必須**可操作**——指出往清理邏輯的哪個方向修，不只描述現象
- 報告首要讀者是「決定清理邏輯怎麼修的人/agent」

## 硬需求（Hard requirements — 違反即設計不合格）

- **H1 唯讀**：絕不修改原始資料。
- **H2 區分 noise 與設計**：重複前綴不全是 noise——刻意的 metadata 前綴、
  parsing artifact（內容重複了獨立欄位）性質不同，須分類並給不同建議，
  且只有真 noise 才扣清潔度分。分類有判斷成分，設計須讓使用者/agent 能覆核修正。
- **H3 同一發現不得跨維度重複扣分**：一個現象只歸入一個維度計分。
- **H4 容許誤判**：報告必須附具體範例讓使用者自行判斷（如技術教學文章講解 HTML
  語法不算殘留）；使用者提供網站/資料集描述時據此調整判定。
- **H5 評分一致性**：同一份資料重複檢查，分數不得漂移。閾值、規則、算術
  不能每次執行臨場重新發明。

## 環境事實（Environmental facts — 實戰得來，設計必須容納）

- **E1 常見資料形態**：爬蟲輸出常為 JSON（內容欄位名 `content`/`text`/`body`/`markdown`
  不一）、markdown 檔目錄、或 SQLite；常帶 `source`/`category` 欄位或以子目錄分來源。
- **E2 實戰見過的 noise 型態**：markdown 化的 nav 連結列表前綴、`[文字](javascript:void(0))`
  按鈕殘留、`%PDF` 開頭的未解析二進位、獨立成行的 UI 文字（Download PDF / Back to top）、
  HTML entity（`&amp;` 等）。
- **E3 Embedding 行為**：大量文件共享相同前綴會使向量在該維度聚集、降低內容區分度；
  超長文件超出 embedding 有效上下文後尾段等於不存在。
- **E4 Code block 誤判**：技術文件的 code block 內出現 HTML/JS 是正文不是殘留，
  偵測需豁免，否則技術站全數誤殺。
- **E5 Model 手算會漂移**：讓 model 每次臨場重新實作閾值比較、regex 掃描、
  扣分算術，跑 N 次會有 N 種結果（H5 的直接威脅）。
- **E6 大資料集不能全進 context**：數千筆內容全文遠超 context 上限；
  設計必須讓逐筆掃描不佔用 agent context。

## 附錄：clean-room 比對實證（2026-07-21）

> 實驗方法：以本規格讓禁讀現有實作的 subagent 從零重寫，與現行實作（prose 下沉重構
> 進行中的版本）比對。本次時序與 deep-review 先例相反——**盲寫先於下沉實作**，
> 收成直接反映進同一輪重構。

**收斂處（機制被需求逼出）**：盲寫版獨立做出與重構方向相同的核心決策——把全部
掃描/閾值/算術下沉為 stdlib-only Python 腳本、固定 seed 分層抽樣、扣分逐筆可追溯、
數字單一來源（SKILL.md 不重述）。E5/E6/H5 三條合起來實質決定了這個形狀。

**已回流的盲寫版知識**：SQLite 以 `mode=ro` URI 開啟（H1 的機械保證）；
`false-positive` 分類（H4 誤判的計分出口）；`--exempt`（context 豁免的計分出口，
杜絕 model 手調分數）；未確認分類必須在報告標示（自主執行 fallback）；
「No example, no finding」等 hard-rule 措辭。

**合法設計分歧（已拍板，維持現行）**：

1. 盲寫版 scan/score 兩段式 CLI + overrides.json 中介 vs 現行單段 `--classify`/`--exempt`
   重跑——重跑是確定性的且成本近零，單段少一份中間檔與一步儀式。
2. 盲寫版把「薄內容」歸 RAG（空佔位歸清潔度）vs 現行兩者皆歸清潔度 4d——
   維持現行語意（薄內容多為清理過度或抓取失敗，修在 pipeline）。
3. 盲寫版全域分 = per-source 加權合成 vs 現行「全域與 per-source 取較嚴重者 + 保底
   半額」——現行偏告警導向（小來源大爛帳不被平均沖淡），維持。
4. 盲寫版連續飽和扣分曲線 vs 現行兩級門檻表——門檻表可直接寫進測試斷言，維持。
5. 盲寫版 JSON 輸出 vs 現行帶前綴標籤文字——沿用本 repo skill 腳本慣例（ship-state
   式、agent 整行引用），維持。
6. **H3 邊界拍板（R4 審查後）**：前綴軸與重複軸嚴格單一維度（4b/4g/4h 一律先剝
   cluster 前綴；dup-group 非首筆不入開頭區分度）；**尺寸軸為有意重疊**——空/薄文件
   同時見於 4d（清潔＝爬取/清理品質，修在 pipeline）與 4h-undersize（RAG＝embedding
   語義量，決定收不收），量測不同現象、視為兩個發現，不屬 H3 所禁的重複扣分。

**規格未涵蓋、只活在實作裡的知識**（未來補進需求層或重構時優先確認）：
校準常數的具體值與理由（抽樣分級門檻、各檢查閾值、扣分點數、綜合分權重 60/40）；
「前綴≈全文即歸重複不歸前綴」的去重路由細節；報告須註明本次使用的
`--classify`/`--exempt` 及理由。
