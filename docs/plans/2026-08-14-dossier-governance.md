# Dossier 與 always-on 治理 — 一天實測後的收斂版

> v1（2026-08-14）。起點是一句抱怨：「很常觸發 dossier flag 超過大小上限，然後就要壓縮或分拆，
> 有點花時間。」查下去發現**大部分不是使用習慣問題，是工具與規範的缺陷**；而過程中三次試圖
> 「加一條規則」，兩次被 fixture 否決。本檔記下裁決與**為什麼**，DO 與 DROP 同等重要。

## Context — 起點的診斷全錯了兩次

**第一次**：以「STATUS.md 負增量」當「被 flag 逼著壓縮」的代理指標，據此算出 krepo 29 次、
evint 8 次。**代理指標是壞的** —— krepo 的負增量多數是拆分搬移與完成項移出生命週期，只有兩次
真由 flag 驅動；且它的量體 flag 早在 2026-07-31 就明文豁免。差點導出「krepo 需要一次性整頓」
這個**被該豁免條款指名為無效工**的結論。

**第二次**：以「always-on 在回漲、沒人知道新內容該不該進去」推論需要內容路由規則。查證後
`claude/CLAUDE.md` 與 root `CLAUDE.md` 自 08-11 收斂後回漲的 +2783 bytes，來源是**一條新地雷
＋三顆 kernel push 授權修訂，四筆都該在 always-on**。

> **兩次都是同一個形狀：憑推論指認失效面，而實地查證不支持。** 這條教訓比本檔任何一項改動都重要。

## 真正量到的事實

**工具缺陷（已修，見「已落地」）**：條目 flag 把緊跟其後的 blockquote 算進前一條（`krepo-mops-major-news`
280B 決策 ＋ 524B 歸檔指標 ＝ 804B，超標 4 bytes）——**而那個指標正是收斂做對之後的產物**；
`DOSSIER_TARGET_PCT` 只套在全檔 flag、條目漏了，於是每次都壓到剛好過關。

**規範與工具矛盾**：`references/dossier.md` 寫「超標時優先歸檔」，而 flag 文字寫「蒸餾＋歸檔」——
**只有 flag 會在動手當下被讀到**。

**反向守門缺席**：`xref-gate` 只驗指標指到的東西在不在，「歸檔出去後沒人連」從沒查過。
實測 evint 6/10、krepo 9/29 是孤兒。

**節分布基準**（七個 repo 實測，供日後判斷用）：

| 節 | 建議 | 依據 |
|---|---|---|
| 關鍵決策 | 25–35% | 健康 repo 21–58%，且它是 dossier 本體 |
| 死路 | 15–25% | **唯一設計上不刪的節**，配額給最大 |
| 技術債 | 10–15% | 償還後移除，半有界 |
| 進行中 | 0–15% | 有工作項時偏高，無則接近 0 |
| 已完成里程碑 | 5–10% | 只留最近一批 |
| 已知缺口 | 5–10% | 健康 repo 4%；dotfiles 曾達 34% |

**dotfiles 的結構下限**：缺口＋死路＋技術債 ＝ 17268 bytes（72%），判準上皆不可歸檔。
**在不違反自身判準的前提下達不到 20889 的建議目標** —— 這不是懶，是結構事實。

**always-on 完全沒有治理**：`claude/CLAUDE.md` 25301 ＋ root `CLAUDE.md` 16993 ＋ `MEMORY.md` 2016
＝ 44310 bytes，每個 session 都載入，**沒有任何大小 gate**；而 22687 bytes 的 STATUS.md（**不自動
載入**）有門檻、flag、建議目標、節佔比、歸檔判準五層。**治理的對象錯了。**

## 已落地（2026-08-14，PR #97／#98）

1. 條目 flag 邊界止於非續行區塊（行首 blockquote／標題／分隔線）。十個 repo 重量：只有出問題
   的那個變（804→722），其餘差 0 —— 精準修復，不是放寬門檻。
2. 條目 flag 補建議收斂目標（800 × 85% ＝ 680）。
3. 全檔 flag 帶收斂順序：**①砍重複 ②歸檔留指標 ③最後才蒸餾**。危險不對稱是理由 —— 歸檔可
   取回，蒸餾砍掉的是理由與實測數字，git history 找得回文字、找不回「當初為什麼認為這個數字
   重要」。
4. 歸檔孤兒反向守門。單次掃描（krepo 13.0s→2.5s）；pattern 用 `.md` 而非 `archive`（**窄 pattern
   的假陽性比多掃幾行貴得多**）。
5. 存量整理：死路分層外移 `docs/dead-ends.md`（5123→3006）、已知缺口六條歸位到決策。

## DO — 證據充分，可直接做

### ① 修 `claude/skills/project/references/dossier.md` 裡「已知缺口」那一列的定義

**唯一測出來的真實混淆**：G9 兩臂各有 1/4 把「上游 API 的 rate limit」放進該節，理由都是
「跟『沒有多幣別支援』那條同性質」。該節名同時讀得成「我方的功能缺口」與「外部系統的已知
限制」，字面上兩者都成立。

**這是修定義、不是加規則** —— 驗證成本 G9 已經付過。**不要在上面再疊一層路由判準**：G9 已證
那救不了（決策樹那臂錯得更難看）。

### ② always-on 量體訊號

先**只加訊號**：不設硬門檻、不砍任何內容、不出題。跑一陣子看實際分布再決定門檻值。

**理由不是「44KB 太大」**（對 1M context 是 3%），是**沒有東西看得住它、而它已經在漲**。
砍內容沒有 gate 守著，兩週後會回來 —— dossier 在 08-06 之前就是那個狀態。

### ③ pre-commit hook 擋 default branch

2026-08-14 實地違規一次：merge 最後一哩切回 `main` 同步 default，**下一輪直接開工、commit 落在
main**。`branch-first.sh` 情況 B 一次救回，未 push 故無外部影響。

**規則本身沒問題** —— kernel 明文、腳本齊備、救援有效。缺的是機械層。值得記的是那個時機：
**merge 收尾的終點正好是下一輪違規的起點**。

## 需先有 fixture — 這些是「我覺得」不是「我測到」

### ④ 軟目標訊號的「結構下限」出口

外部 findings 第 1 條（低於門檻但高於 85% 就提醒）方向對，但套 85% 會讓十一個 repo 有七個
**每次 ship 都印**。而 dotfiles 結構性達不到那個目標 —— 對它，訊號會永遠亮且不可行動，
那正是 krepo 137KB 現在的狀態（**flag 常亮＝沒有 flag**）。

**「已達結構下限」怎麼定義，目前沒有答案。** 這是未解，不是待做。

### ⑤ per-repo 門檻

問題比外部提出者估計的更真實 —— 活躍 repo **無一**在此門檻下寬鬆，寬鬆的全是葉節點／小型
repo（kapi-protocol 67%、krepo-common 56%、aism-api 29%）。

但處方要走 krepo 豁免條款的形狀（**帶理由、帶失效條件、帶不在豁免範圍的 flag 清單**），
不是純數字覆寫 —— 後者缺的正是提出者自己擔心的防濫用。門檻適用性分三層，**不要混成一條**：
被拆的那一份豁免（krepo）／子 repo 照常／已移交不適用。

### ⑥ 缺口滯留的新假設

Scenario 17 推翻了「寫入時分錯」（Sonnet 分得很清楚）。剩下的假設是**演化路徑**：先寫成缺口
（當時尚未決定），後來做了決定就在原地追加「暫不做」，而沒有搬家。要測那個得換情境 ——
「dossier 已有一條缺口條目，本輪對它做出暫不做的決議」，量的是**會不會搬節**。

## DROP — 今天驗證後否決，不要再回頭

| 提案 | 否決依據 |
|---|---|
| 「已決議暫不做屬決策節」寫進 `dossier.md` | Scenario 17：v2 四輪**兩臂零差異**，baseline 自己就把現況缺陷放缺口、決定不修放決策並交叉引用 |
| krepo 內容路由決策樹上收成全域規則 | G9：兩臂各 4 輪**零差異**；且適配句「狀態類不走三題」成了跳過判準的逃生口 |
| 「從超出常態佔比的節收」 | 超出可能來自**誤放**而非該節本身肥（本批缺口 34% 即是）；且要執行得先有常態佔比基準 |
| 條目 flag 與全檔 flag 的張力協調 | 量級約 15 bytes 對 24576，不成比例 |
| OpenWiki | 官方定位為 derived 層（architecture／integrations／workflows），與 dossier 明文不記的東西正交 —— **死路在程式碼裡沒有痕跡，掃描器掃不出不存在的東西** |
| Linear／外部 tracker | 2026-07 已否決：缺的是慣例固化，不是新工具 |
| mem0／Zep／Letta | Letta 的 core/archival 分層架構是對的，但外部服務違反 git 唯一媒介、隨 repo 移交、不引入第二份權威三條硬約束。**同一架構在 repo 內已經有了**：`claude/CLAUDE.md`（9484B always-on）＋ `known-hazards.md`（10019B 按需），1:1 分層、零外部依賴 |

## Meta — 這一天真正的產出

三組成對實驗（外部 findings 逐條驗證、Scenario 17、G9），**落地兩條、否決四條**。共同形狀：
**看起來合理的規則，在樓層模型上 baseline 本來就接得住**。

因此立一條作業原則：**凡「加規則」預設先跑成對實驗；凡「修既有矛盾」或「加機械防線」可直接做。**
①②③ 屬後者，④⑤⑥ 屬前者。

> 附帶一條方法論修正：**「省 context」不是收斂 STATUS.md 的正當理由** —— 它不自動載入。
> 該理由只適用於 `CLAUDE.md`。收斂 dossier 的理由是訊號密度與可讀性，那仍然成立。
