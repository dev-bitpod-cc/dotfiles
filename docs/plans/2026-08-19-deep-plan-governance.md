## 一、使用判準（最高槓桿，且不需要改 skill）

**不是看 repo，也不是看變更大小，而是看：這次改動會不會產生「無法從 diff 反推的宣稱」。**

- **值得跑**：skill body、`CLAUDE.md`／`AGENTS.md`、`testing-contract.md`、STATUS.md 的判準、共用 fixture／eval。這些地方寫錯一個「為什麼」，**測試全綠、diff 看起來完美**，然後每個後續 session 都繼承它。
- **不值得跑**：`scripts/render-ssh-config.sh`、`inventory.sh` 解析、setup 腳本、`shell/functions.sh`。這些**測試就是 oracle**，錯了會紅；事後 `/deep-review` 更便宜且抓同一類東西。

> handoff mtime 那批是邊界案例：程式碼部分不值得審，**是「連帶要改 §13 與 SKILL.md」把它推進值得那一格的**——而假的 `created` 語意正好就要寫進那兩個檔。

**本 repo 的命中率會系統性偏高**（文件即產品，一次改動出貨的 prose 比 bash 多），但那是「該用」的理由，**不是**把結論外推到一般應用程式 repo 的理由。這兩件事必須分開，見〈三〉的邊界。

## 二、撤回：不加輕量路徑

檢討當下我提過「加輕量路徑：小變更 → N=2 單輪、不出 verdict」。**撤回**——資料兩次都指向反方向：

- 他們自己的 **E3**（2026-08-18）量到第二輪：(a) 重述 0 條、(b) 處置引入 3 條、(c) 第一輪沒挖到的 2 條，**含唯一的阻斷級**。
- **本次**第二輪 0 復發 + 2 條新 blocking，兩條都真實（其中「`SKILL.md` 不重述輸出格式」是假前提，會讓我把錯的事寫進權威檔）。

⇒ **第二輪兩次都產出了第一輪拿不到的東西，砍它會直接砍掉本 skill 的一部分價值。**

同時要看清第二輪的**真實職能**：它審的多半不是原計畫，是**我的處置**（本次那兩條都是 Step 4 修訂時新寫進去的論證）。這與 E3 的 (b) 同一形狀。⇒ 處置若只是刪行、沒新增論證，第二輪期望值低；處置若寫了新理由，它守的是一個真實的洞。

**推論**：N=2 已是 E1 量過的下限（N=3 多出來的全是嚴重度分歧、不是新問題），第二輪不能砍 ⇒ **4 次 reviewer 執行是這個設計的地板，成本降不下來**。唯一還沒動過的槓桿是模型層級，見〈四〉。

## 三、建 field log（現在就做）

`claude/skills/deep-plan/field-log.md`，**敘事為主、表格為輔**——真實執行到目前為止總共兩次（krepo 一次 + 本次），N 會長期很小。四列數字什麼都教不了；四段「這次唯一學到的一件事」教得很多。

每次一段：

```
### YYYY-MM-DD · <一句話情境>
計畫: <路徑> · <模型> · N=? · ? 輪 · 改動是否寫進權威檔: 是/否
findings: 第一輪 ? blocking → 第二輪 ? 復發 + ? 新
**會 ship 的: ?/?** — 逐條列出是哪幾條
成本: ~?? 萬 token / ?? 分 · 實作本身 ?? 分
一句話: <這次唯一值得記的觀察>
```

- **寫入時機是 ship 時，不是審完時**——「會 ship 的」要等實作完才答得出來。
- **觸發判準機械化**：這批含走過 `/deep-plan` 的 `docs/plans/*.md` → 補一段。
- **不記**：逐條 findings（計畫檔修訂與 PR body 已有，重複會漂）、reviewer 原文、沒有數字支撐的「感覺有沒有用」。
- **「改動是否寫進權威檔」這欄是為了日後分辨哪些結論可以外推**——本 repo 的樣本會偏向「是」。

### 與 `evals.md` 的分工

`deep-plan/evals.md` 的「執行紀錄」記的是**受控 eval**（有 oracle、有 fixture、可重跑）；field log 記的是**真實使用**（無 oracle、一次性、觀察窗只有當下）。混在一起會讓那份 oracle 檔繼續膨脹（它已有一條 backlog：未經 deep-review）。

⚠️ **本次那列「P4 觸發條件核對」留在 `evals.md`、不搬**（檢討當下我提過要搬，改判）：它記的是 **eval fixture 的狀態變更**（P4 仍待實例化、為何不登記），那是 eval 管理的事實。field log 另記同一次執行的**使用面**數據。兩邊指向同一次執行不算重複——它們回答不同問題。

## 四、需要獨立決定的參數（不在本計畫改）

**模型層級**：本次跑在 **Opus**（session 模型），而全部 evals 校準在 **Sonnet**（樓層模型）。後果有兩個，且性質不同：

1. **成本**：這是唯一還沒動過的降本槓桿（第二輪與 N 都動不得，見〈二〉）。
2. **可比性**：強模型會自己補上規則要求的行為 ⇒ **本次的任何觀察都不能拿來判「某條規則有沒有作用」**。

⇒ 與 `deep-plan` 的 N 預設值同一類：**是一個要刻意做的參數決定，不該在檢討中順手改**。依 backlog 既有形狀記一條。

## 不做

- **不改 `deep-plan/SKILL.md`**——見下節。
- **不改 N**（E1 已量，判準沒定義「有新增時該調到多少」那格，backlog 已有獨立條目）。
- **不把 verdict 拿掉**。觀察到「它沒有承重」（本次判不通過，但決定是使用者做的）——但那是 N=1、且不通過的處置本來就是「交使用者分流」，**流程照設計走了**。要證明它是裝飾，得看到「verdict 說通過／不通過而使用者照著改變行為」或反例累積幾次，現在還不到。

## 證據門檻（為什麼上面幾乎都不動 skill）

本 repo 既有規則（`STATUS.md` 關鍵決策節、memory `skill-rule-change-evidence-bar`）：動 skill 規則要**同情境實測到行為分歧**，且**必須在樓層模型上量**，成對實驗兩臂零差異就撤除。

本次是 **N=1、跑在 Opus、沒有對照臂**。四個觀察（缺輕量路徑〔已自我推翻〕、verdict 沒承重、第二輪在審處置、模型層級不對）**全部只到「值得查」這一格**，沒有一條到「該改規則」。

⇒ 本計畫的產出刻意只有兩樣：**一個使用判準**（不是規則，是我在建議何時載入它時的依據）與**一個累積機制**。規則本體不動。

## 執行順序

1. 建 `claude/skills/deep-plan/field-log.md`，seed 本次實跑 + 使用判準當第一條累積結論。
2. `docs/backlog.md` 記一條：deep-plan 的模型層級待獨立決定（與 N 那條並列，理由同型）。
3. `STATUS.md` 決策節記一條：使用判準 + 撤回輕量路徑提議（後者零 diff，不記就消失）。
4. 跑 `tests/run.sh`（改了 `.md`，交叉引用 gate 要一起綠）。
