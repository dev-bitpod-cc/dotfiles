# 文檔治理 — 目標、現況、問題、困難

- 日期：2026-08-20
- 性質：**計畫目標書**。定義要解什麼、現況是什麼、難在哪。**不含解法提案**——那是下一份文件的事
- 範圍：**dossier 家族的全部文檔類型**，不只 `STATUS.md`

---

## 一、目標

按優先序：

1. **保留這套機制的價值** —— 決策、死路、里程碑、待辦真的被記下來，而且**需要的時候找得到**。使用者明確表態：**「需要或有用處但是查不到，這沒有意義」** —— 任何把內容搬走而不解決可檢索性的做法都不算解
2. **消除治理成本** —— 現況是每隔幾天就要處理一次量體訊號，且處置需要人判斷「收哪一節、哪幾條」。使用者原話：**「花了這麼多成本，再沒幾次又要來了」**
3. **可長久運行** —— 不是再撐三個月，是結構上不會週期性復發
4. **涵蓋所有文檔類型** —— 死路、待辦、歸檔、計畫、規範、skill body、eval 全部納入，不只 `STATUS.md`

### 使用者提出的兩個約束

- **token 成本會跟「每次都要讀取的規模」拉扯** —— 治理本身要讀規範與被治理物；若治理花的比它省的多，就是負 ROI
- **找不到 = 沒存** —— 見目標 1

## 三、問題

**P1｜治理的對象與實際的體積分佈嚴重不符。** 量體機械管 1.9% 的內容，而 96% 的文檔（含最大的 `docs/plans/` 329KB、`eval` 298KB、`skill` 325KB）**沒有任何量體訊號**——不是門檻太寬，是根本沒有量。

**P2｜被管的那一個檔，管法會週期性復發。** `STATUS.md` 有五層訊號、567 B/日、距門檻 680 bytes。它的內容（決策、死路、里程碑）**只增不減**，而容器有上限 ⇒ 撞牆是週期性的，每次都要人判斷收哪一節。

**P3｜「排出去」之後就沒有下文。** 歸檔 28 次 commit 零刪除、13 天無人回頭修改。內容仍在 git 裡，但**沒有機制證明它被找得到**——而使用者的第一優先正是「找得到」。⚠️ 讀取不產生 commit，所以「有沒有被讀」**在 git 裡量不到**，只能量「有沒有被修改」。

**P4｜治理面自己不受治理，而且它比被治理物大。** 49,675 vs 23,896。規範與 gate 本身也是文檔，也在長，也沒有任何訊號看著它們。

**P5｜家族在機隊上未被採用，規範卻是全機隊生效的。** `dead-ends.md` 1/12、`backlog.md` 2/12。任何以「家族齊全」為前提的設計，對 11 個 repo 不成立。

**P6｜同一個工作項會產生大量近似文檔。** `docs/plans/` 兩天內產出 255KB、其中 8 檔是同一件事的不同版本；該目錄的既有規則是 **write-once（不就地改寫）**，於是每次修訂都新增一份完整複本，**而該目錄沒有量體訊號也沒有生命週期規則**。

## 四、困難

### 4.1 硬約束（不可放寬）

- **git 是唯一跨主機媒介**；machine-local 狀態不算數
- **隨 repo 移交** —— 接手者只有這個 repo，不能依賴我方機器上的工具或索引
- **不引入第二份權威** —— 衍生物（索引、快取）可以，但 canonical 只能有一份
- **兩個 agent 並用**（Claude Code／Codex）—— **只服務其中一邊的機制不算解**

### 4.2 觀察到的張力（非理論，是量到的）

- **「有界」與「找得到」在同一個載體上互相拉扯**：內容留在會被讀到的地方 → 該檔無界成長；搬走 → 需要另一套機制證明找得回來，而 P3 顯示目前沒有
- **治理是自我指涉的**：治理規則本身是文檔，加規則會讓文檔變大，而文檔變大正是要解的問題
- **可檢索性量不到**：讀取不留痕。目前唯一的可觀察量是「修改痕跡」與「明示指標數」，兩者都只是代理

### 4.3 判斷成本

現行處置需要人回答「收哪一節、哪幾條、搬到哪」。**這是每次撞牆都要重付的成本**，而它不隨經驗下降——因為每次的內容不同。

### 4.4 機隊異質

12 個 repo 的條目形狀 2 種、歸檔慣例 4 種、家族採用度 1/12～12/12。任何統一設計都要處理「未採用者」與「已有自己慣例者」。
